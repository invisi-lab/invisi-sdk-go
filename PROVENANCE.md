# Independent Provenance client

The Provenance family is separate from the existing transaction circuits and Note/Credit spending APIs. It has depth 32, exactly 11 public inputs, and capacities 10, 20, 40, 80, 120, 160 and 190. The trusted release manifest SHA-256 is `6107789c5c0d24c4130bff05da6d389336feb5ccb247c4030eae5198ab05d762`.

Sync authenticated public artifacts from a local protocol checkout:

```sh
python3 scripts/sync-provenance.py ../invisi-protocol
```

This checks the pinned manifest and every artifact/VK digest before copying 7 independent artifacts and keys into `.cache/provenance/`. Existing main circuit manifests, assets and version numbers remain separate. The cache is generated and ignored by Git. The reviewed manifest is tracked with this SDK; updating its pin requires an explicit release review.

Configure scope (chain and protocol), current chain generation, provider, trusted Ed25519 public keys indexed by signingKeyId, and the reviewed manifest digest locally. Responses never establish trust. Certificate payloads use the fixed 269-byte encoding and raw 64-byte Ed25519 signatures. Empty-tree certificates are supported, but proof sources must contain at least one leaf.

The default service endpoint is `https://provenance.invisipay.fi`. Metadata methods `GetVersion`, `GetStatus` and `GetRules` use chain and protocol deployment scope. There is one configured rule set; no request, certificate, public input or trust context selects a policy. `GetRules` exposes the configured rules and signed signing-key rotation history.

The recommended flow is: fetch a signed root, verify its trust and generation, locally replay paginated public leaves at that fixed root, check contiguous indexes and scoped commitment hashes, verify the final certified root, obtain local membership paths, build the private witness locally, and prove locally. No private opening, owner, nonce, amount, witness, IPN or private key belongs in a service request. The clients reject private-material field names in public submissions. Default membership lookup is a local tree replay; no per-input commitment query is necessary.

Export produces `{operationIndex, proofBundle}`. The bundle has only `format`, `circuitId`, `manifestSha256`, `target`, `publicInputs`, `proof`, and `rootCertificates`; format is `invisi-provenance-proof-v1`, circuit IDs are `provenance_k<K>`, and target is `evm`. Bundle validation checks scope, generation, configured keys, source ordering, sourcesDigest, capacity, operation digest limb bounds, and binding. A host-supplied prover must also verify its output against the authenticated local VK.

Use `evaluateTransaction` / `EvaluateTransaction` / `evaluate_transaction` before broadcast. Successful private-input preflight durably admits one opaque tracking task per scope/generation/native operation digest. Retain its tracking ID and use `getTracking` / `GetTracking` / `get_tracking` or the bounded wait method; normal indexing and the source worker match the transaction and automatically collect its already-verified evidence. No transaction-hash notification or duplicate `submitProof` is required. `submitProof` and proof-job polling remain an explicit direct/self-broadcast fallback. Evaluate, submit and job responses must include matching scope, generation, providerId, signingKeyId and manifestSha256. A generation change requires refreshing canonical roots and local paths; it never authorizes changing already signed calldata. Recognition status is independent of whether a Note has been spent. Normal managed transaction plans persist public source evidence; the independent recovery coordinator below uses its own encrypted namespace for explicit external broadcast workflows.

Source-gated broadcaster quotes bind `keccak256(abi.encode("InvisiBroadcasterProvenanceIntentV1", originalRequestHash))`. Their six signed EIP-712 fields remain unchanged; public metadata contains `provenanceRequired:true` and `requestHashFormat:"invisi-broadcaster-provenance-intent-v1"`.

## Go packages

Import `github.com/invisi-lab/invisi-sdk-go/provenance`. `ScopeHash`, `NoteOpening`, `RecognizedLeaf`, digests and certificate codecs share the protocol golden vectors. `RecognizedTree`, `BuildWitness`, `AuthenticateManifest`, `ExportSidecar` and `ValidateProofBundle` are independent of main proof types.

`NativeProver` requires explicit trusted `NoirExecutePath` and `BBPath` plus a `LoadAssets` callback returning local manifest/artifact/VK bytes. It verifies all public artifact digests, uses a private temporary directory for local witness execution, checks exact expected public inputs, independently verifies with the pinned VK, and removes temporary material. Command errors omit private command output.

`Client.SyncRecognizedTree(ctx, rootID, certificate, maxLeaves)` requires an explicit replay budget. `Client.WaitProofJob` uses the caller context for cancellation and timeout.

The normal broadcaster client derives the Source requirement from verified quote metadata. Public sidecars carry no policy selector.

Configure `sdk.InvisiOptions{Provenance: &sdk.ProvenanceCapability{Client: source, Manifest: authenticatedManifest, Prover: localProver, MaxRootPages: 10, MaxLeaves: 100000}}`. `WithBroadcaster` converges the fee and freezes the quote without Source calls or Source proving. Sign the final EIP-712 statement through `ExportWalletAuthorization` / `WithWalletSignature`, then `Prove` the main transaction. First `SubmitBroadcaster` reads the current service requirement, reconstructs the native statement, checks retained C/NF openings and signed root anchors, rebuilds Source trees locally and proves the smallest supported capacity. It tries the latest checkpoint before bounded history replay. Public evidence is submitted with the unchanged final calldata; private openings and membership paths stay local. No-proof Shield/Credit requests need no Source circuit proof.

Independent Source delivery uses `ready.ProveProvenance(ctx)`, `ready.ExportProvenanceProof(ctx)` and `ready.SubmitProvenance(ctx)`. The same methods exist on managed `session.Operation`, including a recovered, canonically confirmed original payment. Repeated `ProveProvenance(ctx)` validates cached evidence locally against the supplied trusted client; no primary/Source network call, offline prover or local manifest assets are needed. New proofs check `allowedForNewProof` for every selected historical tree, not only the latest checkpoint. Pass `sdk.ProvenanceProveOptions{Reprove:true}` to explicitly replace cached Source evidence after a generation/key update or reorg; failed/canceled reproof retains the prior packet. They do not reprice, resign or resend the payment, and Source generation has no main transaction deadline/spent-input freshness prerequisite. Runtime client/prover capabilities are reattached after restart; encrypted journals retain the original openings, main proof and calldata for reproof.

`ExportProvenanceProof` returns a public `invisi-provenance-submission-v1` packet containing calldata, chain/protocol/token context, main capacity/public inputs, operation digest and sidecars. `sdk.ValidateProvenanceProof` decodes calldata and independently reconstructs the native statement and bindings. `sdk.SubmitProvenanceProof(ctx, client, packet)` submits a serialized packet without account keys, inventory or local prover assets. Keep encrypted openings separately if reproof may be needed.

The prepared plan retains public sidecars, tracking and quote/trust identity separately from its independent Source packet. `ExportProvenanceTracking(ctx)` returns detached acknowledgements. Once the journal records relay submission or uncertainty, repeated `SubmitBroadcaster` looks up the original relay-assigned ID and never sends another payment or requires new-send freshness. Repricing requires explicit new preparation.

Genuine local K10 integration: `INVISI_PROTOCOL_ROOT=../invisi-protocol HARDWARE_CONCURRENCY=4 BB_MSM_LEGACY=1 go test -v ./provenance`.

## Direct submission is independent

Choosing a Broadcaster is optional; its supported-token configuration remains service-authoritative, without a new mandatory client allowlist. Automatic source delegation applies only when `WithBroadcaster` is selected. Ordinary direct preparation, authorization, proving and calldata export do not require or submit a Provenance proof.

For independent delivery, generate public evidence locally and call `Client.SubmitSourceProof(ctx, data, sidecars)`. This accepts the same frozen transaction data before or after payment confirmation; no transaction hash is required. It returns trusted tracking evidence, and the service matches confirmed chain operations automatically. `EvaluateTransaction` remains preflight. `SubmitProof` with an authenticated mined locator remains the explicit low-level proof-job fallback. None of these calls broadcasts a payment or changes its calldata. Recovery remains independent and uses the existing encrypted coordinator/store APIs.

## Signing-key rotation

Pin the provider and genesis signing public key externally. `getRules` may return `initialSigningPublicKey` and public `keyRotations`; these fields never establish trust themselves. Verify the complete history (or an explicitly pinned checkpoint including validity intervals) with `verifyRotationChain` / `VerifyRotationChain` / `verify_rotation_chain`. The shared 169-byte rotation payload uses version 1, provider, old/new key IDs, new public key, activation time and previous rotation hash. Verify the old trusted key signature, SHA-256 new key ID, provider, previous hash, strictly increasing activation times and a caller-supplied current time.

Apply the returned keyring explicitly with `withRotationHistory` / `WithRotationHistory` / `TrustContext::with_rotation_history`; the clients do not accept unknown keys automatically. Historical certificates issued before a key's retirement remain valid; that old key cannot issue certificates at or after the successor's activation. `getRules` alone permits an unknown reported current key so its history can be fetched for explicit verification; proving, evaluation, submission and job responses still require trusted keys.

Optional service membership lookup requires an explicit interest-disclosure opt-in; returned paths are still checked locally against the trusted certificate. Local paginated replay remains the default.

## Independent recovery coordinator

Recovery is opt-in and separate from Note/Credit inventory, signing, reservations and the App. Construct an encrypted recovery store over caller-owned atomic ciphertext records, then inject the current trusted Provenance client and local host capabilities. There is no default plaintext file store. The AES-256-GCM record purpose/AAD binds `Invisi.Provenance.RecoveryRecord.v1`, the namespaced record key and CAS revision; wrong keys, keys from another record, and stale revisions fail closed. Local revisions are bounded to 2^53−1 in all three languages so JSON/CAS round trips remain exact for TypeScript. The host keeps encryption keys and raw openings separately; recovery records contain only public evidence and frozen public transaction identifiers.

Default `prepare` / `Prepare` first authenticates the frozen statement, calls actual preflight and requires an allowed matching tracking acknowledgement. It persists `deliveryMode: "tracked"`, the tracking ID and the complete sidecar, certificates, scope, manifest, generation, operation digest, ordered input nullifiers, operation index, original calldata/hash, signed request hash and base idempotency key with `broadcast_possible` **before returning permission for external broadcast**. A crash after receiving permission cannot make the record unfrozen. The host continues to own its existing transaction journal and input/nonce reservations. `markBroadcast` records a known transaction hash but is not the safety fence. Local cancellation stops proving/polling and never cancels an external broadcast or releases reservations.

`resume` / `Resume` / `run` first calls the injected host's authenticated reconciliation of the original frozen transaction. In tracked mode it polls the persisted tracking capability, checks any matched locator against primary reconciliation and confirms the exact operation through `getOperationRecognition`; it never automatically submits another copy of the source proof. Missing tracking does not silently downgrade. In explicit `prepareDirect` / `PrepareDirect` / `prepare_direct` mode, confirmed locators are persisted before source submission. An uncertain direct-mode network response is retried with the same key, derived as `base:SHA256(canonical JSON proofBundle)` (base: 1–63 printable ASCII bytes, must not start with reserved `internal/`, derived key: at most 128 bytes; checked before permission); a replacement bundle gets a different submission key. The original calldata, callee/scope, token, ordered nullifiers and operation digest remain frozen. The signed request hash also remains fixed, so the coordinator never silently changes nonce, fee or quote. The host must decode/authenticate this frozen transaction and independently verify local proofs; these are required capabilities, not trust inferred from a service response.

In explicit direct mode, after proof submission the coordinator stores the job ID and polls it. **A `valid` job only sets `proofValid`; completion requires `getOperationRecognition` for the exact canonical locator and matching operation digest/nullifiers to return `recognized` with its operation checkpoint.** Mixed funding or dependencies can remain `pending_source` or `source_rejected`; provider outages leave resumable state, and resuming a rejected source operation can observe a later decision without changing any old Note's status. No output Note is required, so a zero-output withdrawal still completes through operation recognition.

Tracking responses are scoped trusted envelopes containing `tracking: {id, status, expiresAt, operationDigest, matched?, reasonCode?, checkpointSequence?}`. IDs are 48 lowercase hex characters; queries send only the opaque tracking ID. Single-operation evaluation has `tracking` on its flat decision; aggregate decisions each carry their own tracking, selected by operation index. States are `pending_confirmation`, `pending_source`, `recognized`, `expired`, `superseded`, and `stale_generation`. Matched/published states require a concrete transaction/block/member locator; SDKs reject unknown states, untrusted identities, mismatched digests/locators and stale-generation capabilities. `expired`/`superseded` are terminal and never trigger another transaction. `expiresAt` is canonical decimal seconds; only the service's authenticated mature chain prefix can establish expiry, so local clock/index lag does not itself expire a task. Bounded waits can time out and be resumed. No-proof public funding/Credit lifecycle operations are already indexed and do not need tracking.

Tracked reproof re-evaluates the unchanged candidate and persists a fresh/coalesced tracking ID before continuing. If the already-mined candidate's original deadline prevents a new preflight, the host must explicitly choose `prepareDirect` with a locally regenerated sidecar and authenticated mined locator; the SDK never changes its deadline/nonce/fee/quote or silently bypasses tracking. Raw openings remain exclusively in host-encrypted storage/local proving capabilities.

Current job wire states are `queued`, `verifying`, `retryable_error`, `valid`, `invalid` and `stale_generation`. `retryable_error` keeps the same job pending for the worker to retry; `invalid` becomes local `proof_rejected` and allows explicit local reproof with a different bundle-derived key. `stale_generation` requires fresh host reconciliation and reproof. Unknown spellings fail closed; none of these cryptographic-job states is a funding/source risk rejection. Public `waitProofJob` returns terminal `stale_generation` immediately and rejects unknown states.

Recovery completion is confirmed by the pinned source service's operation-recognition response under the configured trust model. It is not independent authentication of output Note membership. Receivers still separately authenticate root certificates, canonical anchors and membership when accepting a Note.

A generation change or reorg returns `needs_reproof` after host reconciliation. With explicit local reproof enabled, the host may supply a new sidecar only after the service trust context is explicitly updated to that generation; the coordinator rechecks certificates, binding, ordered input digest and the entire frozen statement. No remote proving URL or raw opening argument exists. On interruption/restart, instantiate another coordinator over the same encrypted records and call resume/run with the same ID. Local `filterRecognizedCommitments` / `FilterRecognizedCommitments` / `filter_recognized_commitments` helpers filter through a rebuilt `RecognizedTree`; protocol spendability and source recognition remain separate, with no per-note network interest query.

Recovery state-machine tests use explicitly marked synthetic proof bytes and real signed root certificates; they validate recovery/encryption behavior and do not claim another native-prover or App integration test.

Go: `NewSQLiteRecoveryRecords(ctx, callerOwnedDB)` creates only the independent `invisi_provenance_recovery` ciphertext table; pass it to `NewEncryptedRecoveryStore(records, key32)`. Alternatively implement `AtomicRecoveryRecords` for your KV. Construct `RecoveryCoordinator{Store: store, Trust: trust, Service: client, Host: capabilities}`; a successful `Prepare` is the broadcast permit. The caller owns the database/key lifecycle.

## Module ownership (1.2.0)

- `protocol/provenance`: public Source contracts, recognized trees, certificates, rotation, trust, manifest and the 11-field layout.
- `prover/provenance`: private Note openings/witnesses, native proving and sidecar creation.
- `rpc/provenance`: HTTP clients, tracking queries and authenticated public tree synchronization.
- `session/provenance`: encrypted recovery storage, coordination and explicit recovery flows.
- Root `provenance`: normal SDK facade and native packet/submission validation; no managed recovery reexports.
